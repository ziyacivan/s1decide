Two stages per ADR 0002 and CLAUDE.md's smoke rule: prove the pipeline on a small same-family
model, then make exactly one 27B QLoRA attempt.

Well inside the five-minute budget. The loss falls and stays noisy, which is what a mixed sample

### The first attempt passed for the wrong reason

It reported a loss of 2.60 falling to **4.17e-07** in 50 steps with every example seen once. That
is not learning, it is a sample with nothing in it to learn.

The selection took the head of `train.jsonl`, and the file is ordered by family. So the run
trained on 200 banking77 rows, 159 of which had the same answer, **and not one `Score` row**. The
ordinal loss and the soft targets — the two newest and least-exercised code paths in the
repository, added the same day — were never entered, while the number on the screen said success.

`select_rows` now samples round-robin across `qtype`, and within `score` across hard and soft
targets. The same 200 examples are now 89 `Noul`, 73 `Score`, 38 `Choice`, with 37 soft targets
and option counts of 2, 3, 4, 5 and 8. Four tests assert the coverage, because the failure mode
here is silence.

## Stage 1 — 27B QLoRA — **failed, and not on memory**

`train/configs/smoke_27b.yaml`, seq 1024, batch 1, rank 8, one attempt as instructed.

```
RuntimeError: A inner dim (5120) does not match weight (1)
  bitsandbytes/backends/cuda/ops.py:857  _gemm_4bit_kernel_impl
  bitsandbytes/autograd/_functions.py:472  matmul_4bit
  unsloth_zoo/temporary_patches/bitsandbytes.py:100  forward
```

It failed in the **forward pass**, not the load, with a shape error inside Unsloth's bitsandbytes
patch. No `train_summary.json` was written because no step completed.

**This is not the OOM the plan anticipated, so the conclusion the plan attached to an OOM does not
follow.** Three things say so:

- The card had 24 GiB free and the process died on a shape assertion, not an allocator.
- `unsloth/Qwen3.8-27B-unsloth-bnb-4bit` loads and runs forward passes on this card through
  `HFEngine`: 300 of them, earlier the same day, for the `Noul` quantization study. The
  checkpoint and the hardware are not the problem.
- The shape `(1)` for a weight is the signature of a **pre-quantized checkpoint handled as if it
  were unquantized**. That is a documented pitfall in this repository, not a new mystery:
  `engine/hf.py` and `data/build/teach_run.py` both carry an explicit fix for it, and the comment
  in `teach_run.load_teacher` says adding our own quantization config on top of a checkpoint that
  ships one "is what broke the 27B load three times in Phase 0". `_load_model` passes
  `load_in_4bit=True` to a checkpoint that is already 4-bit.

So the honest reading is that S1 on the 3090 has **not** been ruled out. What has been shown is
that the Unsloth training wrapper needs the same pre-quantized-checkpoint handling the inference
and teacher paths already have.

Stopping here as instructed rather than iterating: one attempt was the budget.

## Stage 1, attempt 2 — 27B QLoRA — **no OOM, but not the S1 configuration**

Approved 2026-09-23 as one more attempt, same budget: seq 1024, batch 1, rank 8, 200 samples,
50 steps. `results/smoke-27b/` — `train_summary.json`, and `report.md` with the coverage tables
beside `loss.png`.

**The fix worked for the failure it targeted.** `_load_model` now reads the checkpoint's own
`quantization_config` and does not request 4-bit on top of it (`loader.prequantized: true`,
`quantize_on_load: false`). No shape error, 50 steps completed, adapter saved.

| | |
|---|---|
| VRAM peak | see `vram_peak_gib` (20.55 GiB of 24) |
| throughput | see `tokens_per_second` (86.4) |
| wall time, 50 steps | see `elapsed_seconds` (80.8 s, excluding load) |
| kernels | FLA chunk + fused recurrent accelerated, conv1d torch, SDPA — same row as `doctor` |

**But it ran on the fallback, and the fallback is not S1.** Three facts, all in
`train_summary.json` → `loader`:

- **Unsloth did not load it.** Given `load_in_4bit=False`, Unsloth's name mapper rewrote
  `unsloth/Qwen3.8-27B-unsloth-bnb-4bit` to the bf16 repo `unsloth/qwen3.8-27b`, which is not
  cached, and failed offline. So the fix, applied literally to the Unsloth call, sends Unsloth
  somewhere else. The run fell through to transformers + peft.
- **The fallback adapts 16 of 64 layers.** Its `target_modules` are `q/k/v/o_proj`, which exist
  only in the full-attention layers (every 4th). 5.2M LoRA parameters; no MLP, no gated-deltanet
  projections. ADR 0002 requires attention + MLP.
- So **20.55 GiB is the peak for a smaller adapter than S1 would train.** Rank-8 MLP LoRA across
  64 layers adds parameters and optimizer state in the hundreds of MB, and LoRA activations under
  checkpointing; 3.4 GiB of headroom makes it plausible, and it is not measured.

**Coverage.** 50 steps at batch 1 sees 50 of the 200 selected rows. Seen: 9 `choice`, 15
genuine `noul`, 9 stage-1 `noul`, 17 `score` (8 soft); option counts 2, 5 and 8 only — **3- and
4-option questions and `ordinal_control` were selected but never reached**. This run's
`coverage` block was backfilled after the run from the same deterministic selection and
cross-checked against the run's own per-qtype row counts; the summary says so under `backfilled`.

**Loss.** No trend, and none expected: every row is seen once, so per-row loss is dominated by
which row it is. `choice` and stage-1 `noul` sit near zero from the first row — the base model
already solves them — and `score` carries nearly all the remaining loss.

### A falling aggregate hid a rising `Score` loss

With the loss split per qtype, the Stage 0 re-run (same config, now reporting coverage) shows
`choice` 0.61 → 0.03 and `noul` 1.07 → 0.55 while **`score` rises 1.76 → 2.49** (mean of first
vs last 10 rows seen). The 27B shows the same direction, 0.98 → 1.21. The Stage 0 verdict above
("passed", 1.219 → 0.747) was read off the aggregate, which the two easy primitives carry.

Ten-row windows over different rows are noisy, so this is a signal and not a conclusion.

### Re-read against each row's floor — most of the rise is the hard/soft mix

A soft target cannot be fitted to zero loss. For a 0.5/0.5 split cross-entropy bottoms out at
`ln 2`, and the distance term at 0.5 — for *any* prediction on the two levels — so a soft
`Score` row's floor is `ln 2 + 0.3 × 0.5 ≈ 0.843` and a hard row's is 0. The mean over a window
therefore moves with how many soft rows it holds.

`eval/smoke_floor.py` rebuilds each run's seen rows (the selection is deterministic), computes
every row's floor, and reports the excess over it — `KL(target ‖ pred)` plus the distance term's
own excess. Output: `results/smoke-floor-2026-09-23/floor.json`.

| run | soft rows, first → last 10 | raw `Score` loss | floor | excess over floor |
|---|---|---|---|---|
| 0.8B | 4 → 8 | 1.756 → 2.494 | 0.337 → 0.675 | 1.419 → 1.820 |
| 27B | 4 → 6 | 0.985 → 1.211 | 0.337 → 0.506 | 0.647 → 0.705 |

The window's soft share explains about three quarters of the 27B's rise, leaving a residual at
noise level, and about half of the 0.8B's. The remaining +0.40 on the 0.8B is two ten-row
windows over different rows. No other cause is proposed on this evidence: the trainer now logs
`KL`, cross-entropy, the distance term and each row's floor separately
(`train.ordinal_loss.loss_parts`), and smoke runs are one pass over their selection, so the next
smoke answers it with the right metric instead of this one reconstructed after the fact.
