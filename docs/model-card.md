## What this is

`s1decide` answers **typed questions about a piece of state in a single forward pass**, and
publishes how well-calibrated those answers are. Three primitives:

| primitive | question | returns |
|---|---|---|
| `Choice` | one option from a caller-supplied set | probabilities over options, confidence |
| `Score` | position on an ordered rubric | probabilities over levels, expected level, confidence |
| `Noul` | is this statement true | probability |

It is **not a chat model and not a text generator.** There is no decode loop anywhere in the
inference path: each option maps to a single token, and the answer is a softmax over the masked
logits at one position. That is what makes a 64-question call cost about as much as a
1-question call, and it is also why the model stays a standard causal LM — it converts to GGUF
and runs in llama.cpp unchanged.

## Read this before the numbers

Three things about this release are weaker than a casual reading would assume. They are stated
here, at the top, rather than in a footnote.

**BF16 was not measured.** The quantization table below has a hole in it. A BF16 27B forward
pass does not fit in 24 GB, and this release was produced entirely on one 3090. Every number in
this card comes from a **4-bit** model unless the row says otherwise. Deferred to v0.2, which
needs a rented H100 (ADR 0006).

**Calibration is post-hoc, not learned.** Stage 2 is temperature scaling fitted per
option-count bucket on a held-out validation split, at the deployment quantization. The model
was not trained to be calibrated; it was trained to be accurate and then its confidences were
rescaled. Learned calibration (S3, GRPO against a proper scoring rule) is v0.2.

**`Score` is trained largely on synthetic labels.** There is no permissively licensed ordinal
corpus we could use ([ADR 0005](adr/0005-ambiguous-source-licences.md)), so `Score` training
data is generated by two independent open-weight teachers with reasoning on, keeping only rows
where they agree exactly or within one level. Expect `Score` to be the weakest primitive. A
programmatic ordinal control set, labelled by rule with no model in the loop, exists precisely
so a `Score` failure can be attributed to the loss or to the labels.

## Calibration

**Read the Brier skill score before the ECE.** A base-rate control — a predictor that ignores
the state entirely and outputs training frequencies — scores a *better* ECE than the calibrated
model on our own evaluation set, while being about 33 accuracy points worse. That is not a
quirk of our setup; it is what ECE does. So the headline calibration number here is **Brier
skill against that control**, which a non-committal predictor cannot win, with ECE beside it.

table. A result that does not clearly beat both is not a result.

## Latency

One forward pass for every question in a call. Source:
`results/20260917-154732-qwen38-27b-unsloth-bnb-4bit-nf4-bf16-latency/latency.json`,
rendered in `LATENCY.md`. Figures below are the **base model at nf4** on one 3090 at a
1,617-token prefix; the S1 adapter does not change the shape and the release re-runs them.

| questions in the call | median | vs one call each | speedup |
|---|---|---|---|
| 1 | 1,516 ms | 1,526 ms | 1.01× |
| 4 | 1,761 ms | 6,245 ms | 3.55× |
| 16 | 2,621 ms | 25,071 ms | 9.56× |
| 64 | 5,918 ms | 100,450 ms | **16.97×** |

Marginal cost per question at 64: **69.9 ms**. Fitted cost model:
`106.3 ms × passes + 1.283 ms × suffix_tokens`, R² = 1.000.

**These are not flat in the number of questions, and we do not claim they are.** A 64-question
call costs about 3.9× a 1-question call at this state size. Flatness holds only when the shared
prefix is large relative to the per-question text — roughly `prefix_tokens ≳ 61 ×
tokens_per_question`. [ADR 0003](adr/0003-latency-target.md) has the derivation, and records
that an earlier "< 2×" target was retired because it measured the benchmark's state size more
than the engine.

## Intended use and limits

**Use it for** structured decisions over a piece of state where you want a probability and not
just an answer: routing, triage, labelling, gating an automated action on a confidence
threshold.

**Do not use it for** free-form generation — it does not do that. Do not use it for
consequential decisions about people without a human in the loop; the selective-prediction
table above exists so you can set a threshold and route the rest.

**Known limits.**

- `Score` is the weakest primitive and is trained largely on synthetic labels.
- Calibration is post-hoc and fitted per option-count bucket on one validation split; it is
  fitted at a specific quantization and does not transfer to another.
- Above 26 options the model answers through a two-stage path (per-option scoring, then a
  choice over the shortlist), which is a different computation from the single-stage path —
  reported as its own bucket.
- Multilingual coverage is three training languages plus whatever transfers. The unseen-language
  OOD sets are there to show how much that is, not to suggest it is enough.
- Every number here comes from a 4-bit model.

## Reproducing

```
uv sync
uv run task doctor      # must be green; see docs/windows-setup.md
uv run task data        # rebuild the corpus, deterministically
uv run task smoke       # 200-sample end-to-end, <= 5 min on a 3090
uv run task train       # --cfg train/configs/<name>.yaml
uv run task eval
uv run task bench
```

Every published number has a JSON file under `results/` behind it, committed alongside this
card. Re-score any run without a GPU with `uv run task eval --rescore results/<run_id>`.
